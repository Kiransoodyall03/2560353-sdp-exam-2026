1 Service overview
The ARL API is the laboratory’s HTTP support service. It holds the researcher register (who may
control which service), the RTA target catalogue, the alert limits of every service, and a backlog of
everything the services have published to the broker. It does not publish to MQTT itself; the services ask
it to verify researchers and read their alert limits from it.

1.1 General state and routines
• Researchers: each researcher has a code (e.g. arl-as3), a name, the experiments (service codes) they
  work on, and a status. Only active researchers whose experiments include a service may send that
  service commands; the services check this through the verify endpoint, so a command from anyone
  else is rejected (unknown_researcher, researcher_defunct or researcher_not_permitted).
• Targets: the catalogue of named sky targets the RTA can observe by id. Ids are tgt- plus three letters.
• Alert limits: the thresholds the services use to raise alerts, per service. The services re-read them, so
  the API is the single source of truth for every limit.
• Backlog: the API records every telemetry, state and event message published by the services (never
  commands or acknowledgements) and serves it as CSV, up to 7 days per request. On the live
  deployment the backlog also contains history from before the deployment started (for example earlier
  MHE mission days and LWM weather history).

The unit column is the quantity’s unit; the API’s unit field is null for keys without a unit suffix (counts,
ratios, scores, pH). Alerts with no limit (offline, fault and missed-survey alerts, and the OWT reserve,
which is the storage_reserve control) do not appear here.

5 Configuration
